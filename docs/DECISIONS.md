# Decisions and assumptions

Status key: **Decided** (built as stated) · **Provisional** (built, awaiting product-owner confirmation) · **BLOCKING** (external verification required before production).

| ID | Decision | Status |
|---|---|---|
| D-01 | **SQL-first schema with PL/pgSQL financial functions.** SQLAlchemy 2 Core runs parameterised SQL. There's no ORM in financial paths. One code path holds the row locks for every caller, and the invariants are tested against a real Postgres, including concurrency. | Decided |
| D-02 | **Billing period is monthly** (calendar-month interval from activation, in IST). Plan prices are for the whole tier per month, not per unit: Starter ₹1 / 1 unit, Growth ₹50 / 100 units, Business ₹100 / 250 units. Plans are versioned rows, so a price change is a new version. | Provisional |
| D-03 | **Rent never settles into the platform's merchant account.** Online rent needs a *verified* owner payout account, routed by the provider (Razorpay Route / linked accounts, Cashfree Easy Split or sub-merchants). The Razorpay adapter refuses to route until the contract is confirmed, so outside demo mode owners use cash or manual-transfer recording. **Verify with the chosen provider:** multi-owner onboarding and KYC, direct settlement to each owner, UPI intent availability, chargebacks, and whether the platform needs a payment aggregator licence. | **BLOCKING** |
| D-04 | **₹1 Starter.** Built as a real paid plan, not a trial. **Verify:** the provider's minimum transaction amount, the fee on ₹1 (it may exceed the price), GST on the SaaS fee (18% assumed, not yet added to prices), invoicing requirements and refunds. | **BLOCKING** |
| D-04a | **Starter is now ₹10 a month** (plan version 3, 2026-11-07), up from ₹1, which also settles most of D-04's concern about the provider's minimum charge and fees on ₹1. People already on Starter keep the price they signed up at. | Decided |
| D-05 | **Upgrade** charges the full new-plan price and starts a fresh monthly period from activation. Unused days are not refunded (shown before checkout). AI usage in the current period carries over, so switching plans never resets quota. **Downgrade** is scheduled for the next renewal and only if active units fit. **Cancel** stops renewal; access continues to period end, then the 7-day grace period. | Provisional |
| D-06 | **Grace and lapse.** For 7 days after expiry (configurable): existing units keep working, no new units. After grace the account is **read-only**: view, export and record money received, but no new units, charges or bills. Tenants always keep their history and receipts. Tenant online checkout depends on the owner's payout status, not the subscription, so an owner's lapse never blocks a tenant paying what they owe. | Provisional |
| D-07 | **Renewal is manual by default.** Auto-renewal (UPI AutoPay / e-mandate) needs explicit consent and a compliant mandate; the field `renewal_mode` exists but isn't wired to a mandate. | Decided |
| D-08 | **AI allowances.** Starter 0, Growth 10,000, Business 50,000 tokens per subscription period. Per-request caps are 3,500 / 5,000. Spend ceilings are ₹15 / ₹60. Voice: 120 s / 900 s of *server* transcription, which isn't configured; on-device speech-to-text is the default and costs nothing. Accounting: billable = input + output + reasoning tokens as the provider reports them. Cached tokens are counted at full weight. Missing usage is charged as the full reservation. The ₹/token rate in config is an estimate for reservations, so set it from real Bedrock pricing. | Provisional |
| D-09 | **Tenancy end date and tenant email are optional.** Earlier discussions had them mandatory; minimal input wins pending confirmation. | Provisional |
| D-10 | **Allocation policy.** Oldest month first, then rent → maintenance → electricity → water → tax → other. Allocations are never re-shuffled after the fact. | Decided |
| D-11 | **Row-level security deferred.** Isolation is enforced in every query, plus DB triggers and IDOR tests. RLS with a non-owner DB role is the next hardening step. | Decided (tracked) |
| D-12 | **Identity.** Firebase Phone Auth in production. A dev OTP simulator runs locally only, with a fixed code `123456` in demo mode and refusal to start in production. Primary-number change uses Firebase `updatePhoneNumber`, so the Firebase UID and internal UUID stay the same. Recovery without the old phone is manual review only. **Verify:** Firebase SMS quotas and costs for India, App Check, and the support team's recovery procedure. | **BLOCKING** (production setup) |
| D-13 | **Messaging.** Console adapters run locally. SES is implemented. SMS (DLT entity, header and template IDs), WhatsApp (BSP, approved templates, opt-in) and FCM are interfaces only until accounts exist; until then messages are recorded as `failed: provider_not_configured`, never as "sent". | **BLOCKING** (accounts) |
| D-14 | **Tax.** No GST/TDS is computed. Units have a `tax_config` JSON and invoice lines accept a `tax` category, so tax lines can be added once a qualified Indian tax advisor confirms rates, thresholds (for example GST registration on commercial rent) and invoice format. | **BLOCKING** (legal) |
| D-15 | **Notes limit** is 250 user-perceived characters (grapheme clusters). The server uses the `regex` package's `\X` when installed, with an Indic-aware fallback. The DB keeps a 1,000-code-point guard. | Decided |
| D-16 | **Languages.** UI, notification templates and receipts are in all 8 languages. Everything except English is a **first-draft translation** needing native review. Speech recognition availability is checked per device and locale at runtime; the app falls back to typing. | Provisional |
| D-17 | **PDF statements** use WeasyPrint (HarfBuzz/Pango shaping) with Noto fonts in the Docker image, because ReportLab can't shape Indic conjuncts. Without WeasyPrint the endpoint returns printable HTML. | Decided |
| D-18 | **Rate limiting** is per-process (single instance). OTP and recovery limits are DB-backed. Swap to a shared store when scaling out. | Decided |
| D-19 | **Delegated managers / co-owners** exist in the schema (`owner_memberships`) and in authorization (`X-Owner-Account`). The invite UI for managers and the ownership-transfer workflow are advanced workflows not built in v1. | Decided |
| D-20 | **Prorated last month.** `end_date` is the last occupied day (inclusive). | Decided |
| D-21 | **Identity verification (eKYC) is provider-based and outcome-only.** Government ID (DigiLocker / Aadhaar eKYC) + liveness selfie + name match are performed by a licensed provider; PayMyRent stores only the result, flags and a provider reference — never ID numbers, ID images or selfies. Consent is recorded per verification (notice version), can be withdrawn, and verification expires (`RG_KYC_VALIDITY_DAYS`). Inconclusive or partial results go to manual review; a result is never auto-verified unless liveness, face and name all pass. Real (non-sandbox) rent is routed only to owners whose identity is verified AND whose owner details were approved by a reviewer. Reviewer API: `X-Admin-Token` (`RG_ADMIN_TOKEN`, disabled while empty). **Open:** choose the provider (ideally one that also does bank-name verification and payouts, see D-03), DPDP review of consent/retention, manual-review SLA, and a reviewer UI. | **Open** |

| D-21a | **Automatic owner document check (amends D-21), 2026-11-14.** At the product owner's request there is no reviewer and no paid provider for the first small group: the owner uploads a PAN card photo, a live selfie and the first and last page of the property deed; the server reads the text (Tesseract) and compares the selfie with the photo on the PAN card (OpenCV YuNet + SFace), both free and run on our own server (`providers/docs.py`, `modules/owner_docs.py`). If the typed name matches the PAN and the deed, the PAN format/uniqueness and age pass, the face score reaches `RG_DOC_FACE_MIN` and no photo is reused on another account, the owner details and photo ID are marked verified; a property is verified when its address (or pincode) is on the deed pages. **This is screening, not proof**: a photo cannot show that a document is genuine, and the free face model is weak on the tiny photo printed on a PAN card, so thresholds must be tuned from real photos. The photos are kept in the database, encrypted (AES-GCM, `RG_PAN_ENCRYPTION_KEY`), so deletion on request and a retention period must be settled with the lawyer (DPDP). Off unless `RG_DOC_AUTO_APPROVE=true`; every attempt is in the audit log; tries are limited per day. **Before public launch** add an authorised anchor (DigiLocker or a PAN-verification service) and a bank-account name check at payout setup. | **Provisional** |
